## A. 개막 후 확인할 것 (2026년 11월 H리그 개막)

### 🟡 A-1. PBP가 경기 중에 실시간 갱신되는가 — 04·06의 전제

폴링 워커(`src/live`)는 원래 지시서의 `detail.php` 점수 대신 **`playbyplay.php`(PBP)** 를 60초마다 폴링하도록
만들었습니다. PBP에는 득점자, 어시스트, 선방, 2분 퇴장, 경기 시계가 모두 있습니다.
문자중계 페이지(`timeline.php`)에 10초, 30초, 60초 자동 새로고침 기능이 있어서 경기 중
갱신될 정황은 강하지만, **비시즌이라 실제로는 확인하지 못했습니다.**

첫 경기일에 할 것:

```bash
# 1) 서버 로그에서 오늘 경기가 잡혔는지 (매일 06:00 KST, 기동 시)
#    [LivePollerService] 오늘 경기 N건: 5501 두산-SK호크스 15:20 ...

# 2) 경기 시작 20분쯤 뒤, 이벤트가 쌓이는지
psql "$DATABASE_URL" -c "SELECT match_seq, count(*), max(observed_at) FROM live_events GROUP BY 1"

# 3) 라이브 응답
curl -s 'http://localhost:3000/api/game/<SEQ>/live' | jq '{status, source, scoreHome, scoreAway, n: (.events|length), last: .events[0]}'
```

판정:

- **이벤트가 늘어나고 `status`가 `live`** → 정상. 06(득점 푸시)에 득점자 이름까지 넣을 수 있다
- **경기 중에는 PBP가 비어 있고 끝난 뒤에만 채워짐** (폴러가
  `PBP가 끝까지 비어 있었음` warn을 남김) → `timeline.php?match_seq=N&HALF=1|2` 폴링으로
  바꾼다. 이 페이지에는 점수표와 선수별 기록이 있고, "경기상황" 표(`.center_cont`)에
  시간순 행동이 있다. 이것도 안 되면 기능을 줄인다: 위젯은 대기·종료·다음 경기 3상태만 쓰고,
  푸시는 시작·종료 알림만 보내고 득점 푸시와 라이브 액티비티는 보류한다. 앱 화면도 바뀌므로
  앱 쪽에 먼저 알린다
- PBP 행 수가 경기 중에 줄거나 순서가 바뀌는지도 본다. `live_events`는 원본에서 사라진
  행을 지우도록 돼 있지만, 정정이 잦으면 푸시(06)가 취소된 득점을 보낼 수 있다
- 06(푸시·위젯)은 **전체판으로 만들었다.** PBP가 실시간이 아니어도 스스로 줄어들게 짜여 있다:
  폴러가 변화를 못 보면 상태가 `live`가 되지 않아 위젯은 pre → finished만 보이고, 득점 푸시도
  나가지 않는다. 이 경우 확인할 것:
  - 종료 알림은 "폴러가 PBP 변화를 본 뒤 멈출 때" 나간다. PBP가 경기 후에만 채워지면
    시작 +150분 마지막 폴링 때 채워져 있어야 종료 알림이 나간다. 더 늦게 채워지면 종료
    알림이 빠진다 → 그때는 일정의 최종 점수(`scoreText`)를 보고 보내는 경로를 추가
  - 위젯이 `pre`인 채로 시작 시각이 지나면 5분마다 갱신을 요청한다 (의도된 동작)

### 🟡 A-2. 경기 전 페이지 모양

지금까지 본 건 전부 **끝난 경기**입니다. 경기 전·중일 때 다음이 예상과 같은지 봐야 합니다.

- 일정 리스트에 경기 전에도 `match_seq` 링크가 있는가 (없으면 `matchSeq: null`이라
  예측·폴링이 안 된다. 일정 `li`의 `timeline.php?match_seq=` 링크는 경기 전에도 있을 가능성이 높음)
- 경기 전 `scoreText`가 `"- : -"`인가 (→ `scoreHome: null`)
- 경기 전 `detail.php`의 머리글에 날짜·시각이 나오는가 (→ 예측 마감 판정이 여기 달려 있다.
  `startsAt`이 `null`이면 예측이 항상 닫힌다)
- 연장전이 있는 경기의 PBP 표 개수와 `detail.php`의 전·후반 행

### 🟡 A-3. 2026-27 시즌 전환

- 기존·신규 컨트롤러의 `season` 기본값이 `"2025"`로 하드코딩돼 있다. 시즌이 바뀌면 올려야
  한다 (`/api/ranking`만 `"2024"`인 건 웹 하위 호환 때문에 그대로 둔 것)
- 폴러와 위젯은 날짜로 시즌을 계산한다 (8월 이후면 그해). 개막월이 바뀌면 확인
- **지금 로컬 `.env`에 `CURRENT_SEASON=2025`로 25-26 시즌을 고정해 두었다.** 2026-27 일정이
  연맹 사이트에 올라오면 지우거나 `2026`으로 바꾼다. 안 바꾸면 폴러가 새 시즌 경기를 못 잡는다
- 로스터(`player:roster:*`, 24시간 캐시)가 새 시즌 선수로 바뀌었는지 확인. 이적 선수의
  배번과 `playerSeq` 매핑이 여기에 달려 있다

### 🟡 A-4. 푸시 실발송 확인 (06)

**`POST /api/push/test`로 개막 전에 확인한다.** `X-Device-Id`의 그 기기에게만 테스트 알림 1건을
보낸다 (기기당 1분 1회). 응답의 `dryRun`으로 서버가 드라이런인지도 바로 알 수 있다.

```bash
curl -s -X POST https://myhandball.lab241.com/api/push/test -H 'X-Device-Id: <앱의 기기 ID>' | jq
# {"sent":true,"dryRun":false,...} 이고 기기에 "알림이 정상입니다"가 뜨면 FCM → APNs → 기기 도착까지 정상
```

- ✅ 2026-09-24 **운영(미니 PC)에서 실기기(iOS)로 발송·도착 확인.** FCM → APNs → 기기까지 정상
- 앱을 다시 설치하면 **기기 ID가 바뀐다.** 테스트할 때는 운영 DB에서 최근 `device_id`를 확인해서 쓴다
  (`docker compose exec postgres psql -U myhandball myhandball -c "SELECT device_id, enabled, updated_at FROM push_tokens ORDER BY updated_at DESC;"`)
- 집 안에서는 도메인 HTTPS가 안 닿으므로 `curl --resolve myhandball.lab241.com:443:<미니 PC IP> ...`로 호출한다
- Android 실기기 도착은 아직 확인하지 않았다

- ✅ Firebase 프로젝트(`myhandball-226dc`) 서비스 계정 키 발급, 인증 확인 (2026-09-23).
  서버 `deploy/.env`에 넣는 방법은 `deploy/README.md` 6단계. 기동 로그에서 `드라이런 모드`가 사라져야 한다
- iOS는 Firebase 콘솔에 **APNs 인증 키(.p8)** 를 등록해야 도착한다
- 확인할 것: 경기별로 알림 센터에 한 줄만 남는가 (Android `tag`, iOS `apns-collapse-id`),
  무효 토큰이 `push_tokens.enabled=false`로 꺼지는가
- 득점 묶음 창(120초)은 메모리에 있다. 창이 열린 채 서버가 재시작되면 그 묶음은 사라진다
  (다음 득점부터 다시 모임). 인스턴스를 여러 개 띄우면 중복 발송되니 폴러는 한 인스턴스에서만
- **라이브 액티비티(iOS)는 만들지 않았다.** 별도 토큰 채널(ActivityKit push token)과 앱 쪽
  네이티브 작업이 같이 필요하다. 일반 푸시가 자리 잡은 뒤 앱 작업과 함께 잡는다

### 🔴 B-5. 개인정보 처리방침·이용약관 게시

- 앱 설정 화면은 `https://myhandball.lab241.com/privacy`, `/terms`를 연다. Caddy가 API의 정책 웹페이지로

- **공개 전에 두 문서를 사람이 한 번 검토한다.** 실제 기능 기준으로 썼지만 법률 검토를 거친 문서는 아니다.
  이용약관의 "한국핸드볼연맹의 공식 서비스가 아닙니다" 문구가 사실과 맞는지 확인한다
- 이용약관은 부적절한 게시물 신고를 **이메일로** 받는다고 적었다. 앱 안 신고 기능(B-1)을 만들면 4항을 고친다

- 새 앱이 첫 설정 정보(`POST /api/welcome/submissions`)를 계속 보낼지 정해서, 안 보내면 처리방침에서 뺀다

### 🔴 B-2. Rate limit이 실제 IP를 보는지

`@nestjs/throttler`는 `req.ip`를 봅니다. 리버스 프록시(nginx 등) 뒤에서 돌리면 모든 요청이
프록시 IP 하나로 보여서 **전체 사용자가 분당 30회를 나눠 쓰게 됩니다.**

- ✅ `main.ts`의 `trust proxy`를 `TRUST_PROXY` 환경변수로 정한다. 도커에서는 `uniquelocal`
  (사설망의 Caddy 컨테이너를 믿음), 그 밖에는 기본 `loopback`
- 모바일 통신사 NAT로 여러 사용자가 한 IP를 쓸 수 있다. 쓰기에만 걸어 두었지만, 문제가
  되면 `X-Device-Id`를 키로 쓰는 추적자(`getTracker`)를 검토
- 저장소가 메모리라 인스턴스를 여러 개 띄우면 제한이 인스턴스별로 따로 센다. 그때는 Redis 저장소로

### 🔴 B-3. 배포·인증서

- **미니 PC에 도커로 배포한다** (`deploy/`, 순서는 `deploy/README.md`). HTTPS는 Caddy 컨테이너가
  자동으로 발급·갱신한다. 남은 일:
  - **가비아 DNS에 `myhandball.lab241.com` A 레코드(→ 집 공인 IP) 추가.** 와일드카드
    `*.lab241.com`이 회사 서버(`183.101.211.16`)를 가리키고 있어서 전용 레코드가 필요하다.
    집 공인 IP가 바뀌면 이 레코드도 고쳐야 한다 (가정 회선)
  - 미니 PC에서 `docker compose up -d --build` 후 LTE로 `https://myhandball.lab241.com/api/health` 확인.
    **도커 이미지 빌드는 아직 실제로 해 보지 않았다** (작업한 Mac의 Docker가 꺼져 있었음)
  - 공유기에서 **443(가능하면 80도)을 미니 PC로 포트포워딩**. 지금 공인 IP의 80번은 공유기
    관리자 로그인 페이지가 응답한다. 외부에 열려 있다면 원격 관리를 끄거나 포트를 바꾼다
  - 미니 PC의 내부 IP가 바뀌지 않게 공유기에서 **고정 할당(DHCP 예약)**
  - 도메인을 `myhandball.kro.kr`에서 `myhandball.lab241.com`으로 바꿨다. `kro.kr`은 Let's Encrypt
    공용 한도(주당 50개, 모든 kro.kr 사용자가 나눠 씀)에 걸려 발급이 안 됐다 (2026-09-23 실측 429)
  - **앱(`myhandball-app`)의 API 주소도 `https://myhandball.lab241.com`으로 바꿔야 한다**
    (`app_config.dart` 주석의 예시가 `myhandball.kro.kr`)
- 인증서 만료 시 **앱은 통째로 먹통이 된다** (iOS ATS / Android cleartext)
- `.env.example`에 `CORS_ORIGINS`가 없다. 웹 배포 도메인을 넣어야 한다
- 배포할 때 Redis의 `teams:M`, `teams:W`(24시간)와 `schedule:*`(최대 10분) 캐시를 지운다.
  캐시에 팀 이름 통일과 `href` 수정 이전 값이 남아 있을 수 있다

### 🔴 B-4. `synchronize: true`

TypeORM이 기동할 때 엔티티에 맞춰 스키마를 자동으로 바꿉니다. 이제 사용자 데이터(예측,
투표, 응원글)가 쌓이므로 **컬럼 이름을 바꾸거나 지우는 순간 운영 데이터가 날아갈 수 있습니다.**
운영 전에 마이그레이션(`typeorm migration:generate`)으로 전환하고 `synchronize: false`.

## C. 앱 쪽에 알릴 것 (응답이 문서 스펙과 다른 점)

앱의 `HttpHandballApiService`를 만들 때 아래를 반영해야 합니다. 대부분 **필드 추가**라
무시해도 되지만, **nullable이 된 필드**는 모델 수정이 필요합니다.

| API | 다른 점 | 앱 조치 |
|---|---|---|
| 공통 | 날짜는 `+09:00`(일정·상세) 또는 `Z`(라이브·응원글) 두 형식이 섞여 있다. 둘 다 ISO 8601 | `DateTime.parse`면 문제없음 |
| `/api/game/:matchSeq` | 슛 성공률은 원본 도넛 차트(시도 점유율)가 아니라 선수 기록 합산으로 계산한 값. `DR`은 블루카드. 선수에 골키퍼 포함, `position`·돌파·`saves` 등 추가 | 라벨 확인 |
| `/api/player` | **`stats.games`가 `null`** (원본 목록에 경기 수가 없음). 상세에서만 채워짐 | `int?` |
| `/api/player` | 이적·은퇴 선수는 `number`·`position`·`photoUrl`이 `null` | 이미 nullable |
| `/api/player/ranking` | 카테고리 14종, 항목마다 `value`와 원본 단위 `unit`(골, 개, 회, %, P) | 선택 |
| `/api/team/:teamNum` | `homeStadium`은 항상 `null`, `address`·`homeTown`·`foundedYear`는 대부분 `null`. `history`, `seasonRecords` 추가 | 카드 숨김 처리 |
| `/api/game/:matchSeq/live` | **`observedAt`이 `null`일 수 있음** (종료 후 한꺼번에 채운 기록). 지난 경기도 `events`가 채워져 온다. 이벤트에 득점자, `type`, `half`, `clock` 추가 | `String?` |
| `/api/game/:matchSeq/mvp` | 로스터에서 못 찾은 선수는 `playerSeq: null` → 이름으로 투표. 그래서 `myVoteName` 추가. 후보에 `side`, `number` 추가. 상위 5명 밖이라도 표를 받은 선수는 목록에 붙는다 | `myVote`가 null이면 `myVoteName`으로 표시 |
| 쓰기 전부 | `X-Device-Id`는 영문·숫자·하이픈 8~64자 (UUID 형식이면 통과) | UUID v4 권장 |
| 쓰기 전부 | IP 기준 분당 30회를 넘으면 429 | 재시도 안내 |
| 응원글 | 팀별 하루 5개를 넘으면 429. 201자 이상이면 400 | 문구 |

## D. 여유 있을 때 할 것

### ⚪ D-1. 파서 회귀 테스트

테스트 러너가 없습니다. 원본 사이트 개편에 가장 취약한 건 파서라, 실측 HTML을 픽스처로 저장해
두고 파서 결과를 스냅숏으로 비교하는 테스트가 효과가 큽니다. 대상:
`game.service`(상세·선수기록), `player.parser`, `team-detail.parser`, `pbp.parser`,
`schedule.service`의 `parseGame`. 이번 작업에서 교차 검증한 불변식을 그대로 테스트로 쓰면 된다.

- 선수 득점 합 = 최종 스코어
- 선수 어시스트 합 = 양팀비교 `AS`
- PBP의 `goal` 행 수 = 최종 스코어 합, 득점자별 골 수 = 선수기록
- 정규리그 시즌 합 = 통산 표
- 팀 상세 `results` 길이 = 순위표 `played`

### ⚪ D-2. 경기 상세에 `playerSeq` 붙이기

`detail_player_record.php`에는 `player_seq`가 없어서, 01 응답의 선수에는 `playerSeq`가
없습니다. MVP(05)는 로스터(배번+이름)로 찾아 붙이고 있으니(`PlayerService.lookupPlayerSeq`),
같은 방식으로 01 응답에도 붙이면 앱에서 경기 기록 → 선수 상세로 바로 이동할 수 있다.

### ⚪ D-3. 기존 3개 서비스의 에러 처리

`/api/schedule`, `/api/ranking`, `/api/team`은 원본 요청이 실패하면 그대로 500을 냅니다
(웹 하위 호환 때문에 손대지 않았음). 응답 모양을 바꾸지 않는 범위에서 빈 값 + 로그로 바꿀 수 있다.
