# 04. 폴링 워커 — 실시간 스코어와 경기 상태

경기 중 연맹 사이트를 주기적으로 받아 **점수 변화를 이벤트로 기록**하고,
경기 상태(예정/진행/종료)를 판정합니다.

**선행: 01번(경기 상세)이 끝나 있어야 합니다.** 폴링할 파서가 필요합니다.

## 먼저 — 이 작업의 전제를 검증하세요

이 작업 전체가 **하나의 검증되지 않은 가정** 위에 있습니다:

> 연맹 사이트가 경기 진행 중에 점수를 갱신한다

문서를 쓴 시점(2026-09-23)이 비시즌이라 **종료된 경기만 볼 수 있었습니다.**
경기 중 화면을 확인하지 못했습니다.

### 판별 방법

개막(11월) 후 실제 경기가 열리는 시간에:

```bash
# 오늘 경기의 match_seq를 찾는다
curl -s 'http://localhost:3000/api/schedule?gender=M&season=2025&type=1&month=11' \
  | jq '.days[].games[] | select(.startsAt) | {matchSeq, startsAt, home: .home.name}'

# 경기 시작 후 5분 간격으로 두 번 받아 비교
for i in 1 2 3; do
  curl -s "https://www.koreahandball.com/game/detail.php?match_seq=<SEQ>" \
    | grep -oE '<span class="(win|lose|draw)">[0-9]+</span>' | tr '\n' ' '
  echo "  ← $(date +%H:%M:%S)"
  sleep 300
done
```

**점수가 올라가면** 이 문서대로 진행하세요.
**경기 종료 후에만 값이 채워진다면** 04·06번은 설계를 다시 해야 합니다.
그 경우 아래 "폴링이 안 될 때"를 읽고 사용자에게 보고해 주세요.

일정 목록(`schedule_list.php`)의 점수가 먼저 올라갈 수도 있으니 둘 다 보세요.
그쪽이 더 가볍기 때문에 폴링 대상으로 더 낫습니다.

## 배경

Flutter 앱과 (앞으로 만들) 홈스크린 위젯이 이걸 씁니다:

- **경기 상세 > 중계 탭** — 시간순 이벤트 타임라인
- **홈 카드 / 일정 카드** — LIVE 뱃지와 실시간 점수
- **위젯** — 대기 / LIVE(실시간 스코어) / 종료 / 다음 경기 4상태
- **득점 푸시** (06번)

## 무엇을 얻을 수 있고 없는가 — 정직하게

폴링은 **팀 점수만** 봅니다. 그래서:

| 얻을 수 있음 | 얻을 수 없음 |
|---|---|
| 실시간 점수 | 득점자 이름 |
| 득점 시각 + 누적 스코어 | 선방·2분 퇴장·경고 이벤트 |
| 경기 상태 판정 | 전·후반 구분 (경기 중에는) |
| 득점 푸시 트리거 | |

즉 **중계 탭은 경기 중과 경기 후가 다릅니다**:

- 경기 중 → `"18' 12 : 10"` 점수만 있는 타임라인
- 경기 후 → 01번의 선수별 기록으로 보강

이 차이를 응답에 명시해야 앱이 적절히 표시합니다 (`source` 필드).

## 폴링 스케줄

경기 없는 날 요청이 거의 없도록, **일정 기반으로 켜고 끕니다.**

`/api/schedule`의 `startsAt`(01번에서 `<tr id>` epoch로 추가한 필드)을 씁니다.

```
매일 06:00        일정 갱신 → 오늘 경기 목록 확보
경기 시작 -10분    폴링 시작
경기 중           60초 간격
마지막 점수 변화 후 20분 또는 시작 +150분  폴링 중단, 최종 기록 저장
```

- NestJS `@nestjs/schedule`(`ScheduleModule`)을 씁니다.
  `package.json`에 없으면 추가하세요
- 경기 2개가 동시에 열릴 수 있으니 경기별로 독립 폴링합니다
- **요청 간격을 60초 밑으로 내리지 마세요.** 남의 사이트입니다.
  `robots.txt`는 전면 허용이지만 예의의 문제입니다
- 실패(타임아웃·5xx)는 지수 백오프로 재시도하되, 연속 5회 실패 시 그 경기
  폴링을 중단하고 `error` 로그

## 저장

Postgres(TypeORM)를 씁니다. `src/welcome/welcome.entity.ts`가 기존 예시입니다.

```ts
// src/live/live-event.entity.ts

@Entity("live_events")
export class LiveEvent {
  @PrimaryGeneratedColumn()
  id: number;

  @Index()
  @Column()
  matchSeq: number;

  /** 경기 시작 후 경과 분. 폴링 시각 - startsAt 으로 계산한 추정치 */
  @Column()
  minute: number;

  @Column()
  scoreHome: number;

  @Column()
  scoreAway: number;

  /** 이 관측에서 늘어난 쪽. 둘 다 안 늘었으면 저장하지 않는다 */
  @Column({ type: "varchar", nullable: true })
  scoredBy: "home" | "away" | null;

  @CreateDateColumn()
  observedAt: Date;
}
```

```ts
// src/live/match-state.entity.ts

@Entity("match_states")
export class MatchState {
  @PrimaryColumn()
  matchSeq: number;

  @Column({ type: "varchar" })
  status: "pre" | "live" | "finished";

  @Column({ type: "int", nullable: true })
  scoreHome: number | null;

  @Column({ type: "int", nullable: true })
  scoreAway: number | null;

  @Column({ type: "timestamptz", nullable: true })

  @Column({ type: "timestamptz", nullable: true })

```

**점수가 변하지 않은 관측은 저장하지 마세요.** 이벤트 테이블이 폭발합니다.

### 경기 상태 판정

지금 `/api/schedule`은 상태를 주지 않고, v1 웹이 클라이언트에서
"시작 ~ 시작+2시간이면 LIVE"로 추정했습니다. **이걸 서버로 올립니다.**

```
startsAt이 미래                              → pre
startsAt 지남 & 점수 변화가 최근 20분 내      → live
startsAt +150분 경과, 또는 20분간 변화 없음   → finished
startsAt 지났는데 점수가 한 번도 안 변함      → pre 유지 (연기·미반영 가능성)
```

마지막 줄이 중요합니다. **폴링이 안 되는 사이트일 때 모든 경기가 영원히 LIVE로
보이는 걸 막습니다.**

## 만들 엔드포인트

```
GET /api/game/:matchSeq/live
```

```ts
export interface LiveEventItem {
  minute: number;
  scoreHome: number;
  scoreAway: number;
  scoredBy: "home" | "away" | null;
  observedAt: string;          // ISO 8601
}

export interface GameLiveResponse {
  matchSeq: number;
  status: "pre" | "live" | "finished";
  scoreHome: number | null;
  scoreAway: number | null;
  startsAt: string | null;
  lastChangeAt: string | null;

  /** 이벤트 출처. 앱이 표시를 달리한다 */
  source: "polling" | "final";

  events: LiveEventItem[];      // 최신순
}
```

`source`:

- `"polling"` — 경기 중 폴링으로 만든 점수 전용 타임라인. 득점자 없음
- `"final"` — 경기 종료 후. 01번의 선수별 기록으로 보강 가능

### 기존 엔드포인트에 상태 추가

`/api/schedule`의 `GameItem`에 추가 (**기존 필드는 그대로**):

```ts
export interface GameItem {
  // ... 기존 ...
  matchSeq: number | null;      // 01번에서 추가
  startsAt: string | null;      // 01번에서 추가
  status: "pre" | "live" | "finished" | null;   // ← 이번에 추가
  scoreHome: number | null;     // ← 숫자 점수도 함께
  scoreAway: number | null;

```

`scoreText`는 **남겨 두세요.** 기존 웹이 씁니다.

## 캐시

- `/api/game/:matchSeq/live` — **캐시하지 않습니다.** DB를 직접 읽습니다
- 01번에서 "진행 중 경기는 캐시하지 않는다"고 한 규칙이 여기에 맞물립니다
- `/api/schedule`의 캐시 TTL을, 오늘 경기가 있는 날에는 60초로 줄여 주세요

## 검증

```bash
# 상태가 붙었는지
curl -s 'http://localhost:3000/api/schedule?gender=M&season=2025&type=1&month=11' \
  | jq '.days[0].games[0] | {matchSeq, startsAt, status, scoreHome, scoreAway, scoreText}'

# 종료된 경기의 라이브 응답
curl -s 'http://localhost:3000/api/game/5490/live' \
  | jq '{status, source, scoreHome, scoreAway, events: (.events|length)}'
```

종료된 경기는 `status: "finished"`, `source: "final"`이 나와야 합니다.
과거 경기는 폴링한 적이 없으니 `events: []`가 정상입니다.

**실제 경기 중 검증**은 개막 후에만 가능합니다. 그때:

- 60초마다 점수가 갱신되는가
- 득점 시 `live_events`에 행이 늘어나는가
- 경기 종료 20분 후 `status`가 `finished`로 바뀌는가

## 폴링이 안 될 때 (점수가 실시간 갱신되지 않는 경우)

이 경우 **정직하게 기능을 줄여야 합니다.** 억지로 만들지 마세요.

1. `status` 판정은 그대로 유용합니다 — `startsAt` 기준 시각 계산만으로
   `pre`/`finished`는 정확합니다. `live`만 못 씁니다
2. 중계 탭은 **경기 종료 후 선수별 기록만** 보여줍니다.
   경기 중에는 "경기가 끝나면 기록이 올라와요" 안내
3. 위젯은 **대기 / 다음 경기 두 상태**로만 출시합니다
4. 06번(득점 푸시)은 보류하고, 대신 **경기 시작 알림**만 만듭니다
   (`startsAt` 기반이라 폴링이 필요 없습니다)

이 결론이 나오면 앱 쪽 화면도 바꿔야 하므로 **사용자에게 먼저 보고**해 주세요.
